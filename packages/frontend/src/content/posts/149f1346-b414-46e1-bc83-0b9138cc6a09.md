In 2026, software engineering changed quite a bit, to the point where I hardly recognize my job anymore. This is not to say I don't like my job, it's just not the same, for better or worse.

The way I see it, AI allows for faster iteration and faster development time all the while doing less work.

This makes us output more software and more products! Great, right?! Well, yes, if you favor quantity over quality that is.

I see agents writing specs for project managers, to then be given to devs so their agent can review it, so that it can be dispatched to yet another agent for implementation. Guess who's doing code review? That's right, another "review specialist" agent. This works great, the review agent will just comment "LGTM" and we'll merge it right away!

Cool, now you ask your agent to publish your app to production.

Great, after a few minutes and a few secret keys committed, your app is live!

```
$ agent run --task "ship the pricing page"
✔ spec.md written
✔ reviewed by agent: "LGTM, no concerns!"
✔ implemented in apps/web (14 files changed)
✔ deployed to production

$ git show 8d4e0b --stat
 .env.production | 1 +
 1 file changed, 1 insertion(+)

+ STRIPE_SECRET_KEY=sk_live_51H8...
```

Now you have yet another app that looks like the thousands of other apps vibe-coded last month! Neat.

Again, as I said, if all you care about is shipping quantity over quality, don't mind me. As for myself, I take pride in knowing actual software engineering, architecture and actually thinking about problem solving. I also **enjoy** configuring my dev environment, my Neovim config and dotfiles; whereas telling Claude "make no mistakes" to build a todolist seems far less enjoyable.

All of that to say, I'm tired of this AI psychosis but I also realize it's not going anywhere.

So, how do I keep enjoying my job in this new era? Well, I keep building but not for the same purpose.

## Letting the agents loose

I'm not going to stop the rest of my team from using agents, it's not happening. However, on the current projects I'm working on, very few people **know** the codebase whereas I **do**.

I think this is a crucial thing to keep in mind nowadays. Your agent will **seem like** it knows the codebase, but really it's just sycophancy. Without the right guardrails, nothing (not even your prompt engineering skills) will stop the agent from shitting code out to accomplish the goal.

Now for a concrete example, I maintain a legacy codebase alongside its modern stack counterpart. On this project, agents have a tendency to simply forget that we have any legacy at all, and only implement features on the **modern** stack. Now, without someone **knowing** that the same feature has to be implemented on the legacy side, i.e., the production, well we'd have a hard time deploying features that simply do not exist.

```
my-project/
├── apps/
│   ├── web/          ← agent implemented the feature here ✓
│   └── legacy-app/   ← the actual production. nothing. ✗
```

Now, you're probably thinking, that's a skill issue, and while you're right, that's not the complete truth. Sure you can instruct your agent to "make no mistake", add an AGENTS.md file or even an agent skill, but agents being non-deterministic, I **know** for a fact something **will** go wrong and junior devs are going to have a bad time.

On the same note, on **every** project I work on, agents just LOVE to add tests. They just love telling me "CI is all green! Typecheck passed too!". Then I go read the tests, and it's just mocks. Mocks everywhere.

Here's an example of tests that agents just love to write, for safety!

```ts
mock(myFunction, () => {
  return () => true;
});

it("should be true", () => {
  const res = myFunction();

  expect(myFunction).toHaveBeenCalled();
  expect(res).toBe(true);
});
```

No shit `myFunction` was called! You called it yourself! And we're not even testing the function's actual implementation...

No matter the amount of skill optimization and AGENTS.md tweaking, the agents would just find a way to not do as told. But it takes someone **who knows this is a bad test** to stop and think about the problem in the first place. To a junior dev or a vibe-coder, this would look just fine.

As a matter of fact, an agent reviewing this code would most likely say "LGTM, this has 100% code coverage!" And we all know code coverage is the most important metric right?

## Keeping agents on a leash

I don't think this kind of low quality code is going away, not anytime soon anyway. So I started building guardrails for my agents, so we can limit the slop. I say limit because there's currently no way to 100% stop the slop, agents will always find a way to circumvent rules.

### 1. Non-deterministic approaches

I started writing more specific skills, with precise instructions and "good pattern / bad pattern" examples. This works as the first step in ensuring the agents "one shot" code and tests. Now this is not a hard rule, nothing stops your agent to just skip these instructions or to rationalize and think "this is not needed for a 1 line change... let me skip this".

But it's something.

> I have had a great success rate telling agents to write skills with [_another_ skill](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md).

### 2. Deterministic approaches

Now this is the real deal, and this is what I still enjoy doing, writing deterministic rules and dev tools!

This is nothing new btw, it's just more important than ever.

First thing I did was set up the strictest possible **linting** rules to enforce **code quality**. That allows us to catch things such as bad patterns, using test mocks, duplicating code and so on. Keeping the rules to their strictest setting is the most important part here, if kept too loose, your agent WILL ignore patterns from the rest of the codebase to invent new ones.

Using pre-built lint rules is not enough however, the projects I work on have very specific things to watch out for, so I could not catch these with existing rules. So I set out to write new lint rules from scratch!

For example, I wrote a very specific [Oxlint](https://oxc.rs/docs/guide/usage/linter.html) rule to enforce integration tests to have at least one accessibility test with [axe-core](https://www.npmjs.com/package/axe-core). This was critical for the project so agents and humans alike do not neglect accessibility which is an exceptionally important subject nowadays.

I also wrote another one to stop type casting with `as unknown as SomeType` which used to be an uncommon pattern, but is now used by LLMs to bypass type interfaces. Especially in tests, which is one of the most important places to **enforce** interfaces!

```ts
// oxlint-disable-next-line no-unsafe-cast - needed for the test fixture
const user = payload as unknown as User;
```

These lint rules error out locally AND in the CI which makes it impossible to merge sloppy PRs. But again, agents WILL find a way to circumvent these rules, after all, lint rules can be disabled fairly easily on a per-line basis, and agents won't hesitate to do so to tell you "CI is green!". This is where a human is still required to ensure this does not happen, as "review agents" probably won't catch these.

## Code review is more important than ever

So now comes code review. What's the point of code review? Catch potential bugs, catch unsafe code and ensure the codebase remains maintainable for the next person.

Now, if we let an agent do the code review alone, it might catch some typos and _some_ unsafe code. But it sure won't ensure your codebase stays maintainable. It won't tell you that this function already exists in the codebase or that this very specific function call will break the initialization of your app. It just won't.

A human who knows the codebase like the back of their hand however, will.

I'm not saying AI code review is bad, I just think the human role is critical for the review to be meaningful.

Also, if you're planning on having a human do the code review, please stop "slop generating" PR bodies, it is absolutely horrible to read. I am a strong believer that well written code is usually enough to understand a PR and that the PR body should just help the reviewer in their review. Like, I don't need you to tell me you wrote an "isEven" function, I can see that!

## Keep honing your skills

I have seen senior devs fail to think critically of AI and just output the sloppiest code. I think it takes a lot of will and determination to see past the psychosis. And this scares me the most, if seniors succumb to AI just as easily as juniors, then what makes them senior at all anymore? Seems to me like it's just a race of who can automate themselves out of a job first.

This is not to say I have not met amazing engineers that use AI for what it is, a tool. But the sad reality is that I think great engineers are a dying breed.

Anyway, my message is, to keep honing your **human** critical thinking skill as well as your technical skill which is **still** needed to keep producing good software.

## Conclusion

After what I said, would you believe me if I told you I use AI agents every day?

And yet, I do. I've used pretty much every model, every harness and probably gave way too much money to evil billionaires destroying the planet... I'm getting carried away, sorry.

I'm not against it, I realize we **can** go faster without just producing more slop, it just takes effort. Effort that most people aren't willing to put in anymore.

I am just sick of this hypocrisy, where we're told writing code by hand is "so over", that Claude was able to rewrite your todo list in Rust in 1 hour, that you can make 10K a month by staying in your underwear and prompting Claude. It's just not happening. Let's all just close LinkedIn and X, and go out to touch some grass.
